# AGENTS.md — src/renderer/src/components/chat

The native-agent chat panel: message feed, streaming deltas, tool-call cards, permission/question
prompts, message queue, and the composer (input + image attach + @-mention). Renders `ChatEvent`s
pushed from main over IPC (`window.api.onChatEvent`).

## Key files

| File | Responsibility |
|---|---|
| `ChatPanel.tsx` | Main container: subscribes to chat events, owns feed state (items/todos/queue/pendingPrompt), rAF-batches stream deltas, opens a new assistant bubble on each `step-start` (ids carry a sequence counter so same-millisecond bubbles never collide) and pins that bubble as the step's delta target (`stepBubbleIdRef`), so a step that streams reasoning, announces a tool call, then keeps streaming appends to the SAME bubble instead of splitting one thought across two; a `tool-start`/`tool-result` flushes the rAF delta buffer before appending its row, so the thought stays whole and above the tool it announced and, on `step-discarded`, drops that step's bubbles and shows a transient notice (feed-only, cleared on the next delta or turn end): `[meow] Model started repeating itself — recovering (n/3)` while automatic recovery is climbing (the event carries a `recovery` level), else `[meow] Model kept repeating itself — waiting for your answer` once it is exhausted and the turn has paused to ask the user (see `docs/reference/09-ui-guide.md` §9.5); a `done` event with `reason: 'stuck'` (Stop or a dismissed prompt) renders a `Stopped: …` error item instead, and reconciles transcript loads with live rows by stable item id; `tool-start`/`tool-result` are idempotent upserts, so a load race or missed start event cannot hide a completed tool result. The render map folds every run of 2+ consecutive `tool` items into a single `cluster` row via `clusterToolRows` (a pure helper that walks `items` and emits the cluster variant at render time — state stays flat so paging and live upserts are unchanged); lone tool calls and any non-tool rows pass through. **Every** tool call renders inside a cluster (even a lone call), and empty assistant messages (no text / reasoning / images) are dropped from the rendered feed — without that drop, the agent's persisted transcript would scatter otherwise-consecutive tools across 1-tool clusters on reload. Reasoning-only assistant messages between tool calls join the run as `thought` steps rather than breaking it. Renders feed + composer + context footer. Feed, prompt popup and composer all sit on the shared centered chat lane (`--chat-lane-w` in `styles.css`; see `docs/reference/09-ui-guide.md` §9.5) — the feed keeps the full panel width and reserves its scrollbar gutter so the scrollbar stays on the panel edge while its rows align with the input card (`tests/e2e/chat-lane.spec.ts`). The todo list renders as a feed row (`TodoCard`) right above the pending prompt, so it scrolls with the transcript. Renders `FeedMessage` for chat entries with hover copy action bar on assistant messages. Reasoning renders chrome-less (`<details class="chat-reasoning">`: `Thought` label, mono word count, trailing caret — no box, no fill, no left rule), the same pattern as a tool-cluster header, so a loose thought does not read as a third row style beside the `Ran a command` line. The count comes from `countWords` (words, not a guessed token figure) and stays visible when the note opens. An incoming delegated message renders as a user bubble with a `delegation` badge and a `From session: <name>` label (`From: <name>` when `isExternalPeer(peerAgentId)`, i.e. an external delegation) (`.chat-delegation-label`); the metadata travels on `FeedItem`/`toFeedItem` so a reload reproduces it, and `direction: 'result'` rows stay unlabelled. Renders Question/Permission prompts with type badge tags (`QUESTION` / `PERMISSION`). Question prompt text renders via `MarkdownText` (full markdown support); the card has no height cap and no overflow of its own — the feed is already the scroll container, so a long question grows the card and the transcript scrolls instead of nesting a second scrollbar inside it, and the prompt header is therefore not sticky (it would resolve against the feed and pin itself to the feed's top edge while the card is in view). Transient status lines (compaction, retry) live only in feed state — never written to the transcript; a failed turn is the exception: it is persisted as an `error` transcript item and rendered as a `.chat-error-card` (red left rule, title, message, Copy) with a `Retry` button (`.chat-error-retry`) when the error is retryable — the button calls `window.api.retryChat(agentId, errorId)` and is disabled while running, and the card disappears on the `error-removed` event. A `notice` ChatEvent (e.g. `/compact`'s "Nothing to compact yet.") appends a feed-only `notice` row. The retry line shows `(attempt N/M)` for rate limits and `(attempt N — waiting for the network/API to recover)` for unbounded retries. On mount it restores an in-flight permission/question prompt via `window.api.getPendingPrompt` so a remounted panel doesn't leave the agent hanging. The prompt box is the **last row of the chat feed** (the meow-chatui `PromptCard` placement), not a composer child: it scrolls with the transcript it interrupts, and a prompt arriving while the user is scrolled up calls `jumpToEnd()` to bring it into view (the agent is blocked until it is answered), with a header + collapse toggle (keeps a one-line summary while collapsed). A question prompt has a header × (`.chat-prompt-close`) and one footer action row — `[Submit] [Skip]` for multi-select, `[Skip]` for single-select — while a free-text answer is input-only (Enter submits, no Send button). Skip (×, footer, or Esc outside the field) declines to answer and ends the turn — the same `window.api.stopChat(agentId)` the composer's Stop calls, so the tool reports the question as unanswered and the next turn still sees it — and clears the prompt locally as well, so the card cannot linger when the turn had already finished and no `done` event is coming. Multi-select rows use a filled-square checkbox (`.chat-check`) and a soft accent tint (no left bar); the labels come from the model (`submitLabel` / `skipLabel` / `customLabel`). Permission prompts are unchanged (Deny already covers them). The composer stacks the queued-messages card (`.chat-queue`, only while non-empty: header with count + caret toggle, then one row per message with send-now / edit / remove actions) above the input card, with a one-line `chat-footer` under it — project folder name + git branch chip (opens the Git view) on the left, context readout + `ModePicker` on the right. The `gitBranch` prop comes down from `App` via `SessionPanes`/`Pane`. Listens for window `meow:composer-insert` events to insert text into the composer (e.g. from the session terminal panel context menu). Older history is paged in 50-item windows as the feed nears the top; that auto-page is suppressed while the session-load pin is settling (`isPinning()`), because the pin writes `scrollTop` on every frame and a mid-pin read looks like "the user is at the top" — paging there prepended a window the pin could not compensate for, leaving the feed far above the bottom of its window. Memoized. |
| `useChatScroll.ts` | Feed scroll controller: follow/anchored/manual modes, turn-top anchoring, jump-to-end, jump button, and `isPinning()` (whether the session-load pin's settle loop is still running, so callers can tell a transitional scroll write from a user gesture). A turn anchor stays armed for `CHAT_ANCHOR_HOLD_FRAMES` after the row first reaches the inset: rows above it can still resolve their content-visibility height and push it down, and once released nothing repairs it (`following` only scrolls down, and the turn bottom is already above the fold). Detach is gesture-driven: only wheel, touch, keyboard nav, or a scrollbar drag leaves follow mode — a `scroll` event observed off the bottom while the DOM itself grows (streamed deltas, `content-visibility` rows resolving their height, history paging) must NOT detach it, so `scrollEventAction()` classifies each scroll event into none/follow/detach instead of trusting the position alone. Once the user scrolls away (manual mode) following only resumes at the literal bottom (`isAtTrueBottom`), not the loose 80px follow zone — re-arming there on a long, still-streaming turn would snap the viewport back down on the next delta (up/down jitter). `chat-scroll-geometry.ts` holds the pure geometry helpers. |
| `ChatInput.tsx` | Composer: **one rounded card** holding everything — an edit banner, image/mention chips, the auto-growing field (`rows=1`, `field-sizing: content`, capped at 8 lines, then scrolling) and, on its own bottom row (`chat-input-bar`), the `+` add menu, the model picker and a right group (variant picker + one round 2.25rem button): Send (arrow) at rest (disabled when empty or while image is loading; allows submitting image-only messages), Stop while a turn runs, Send again (check, `Save edit`) while a queued message is edited. Enter sends, Shift+Enter inserts a newline, Esc cancels an edit when no menu is open, Alt+Enter sends the head of the queue now (`onSendQueuedNow`). Paste/drop image chips (≤4, ≤5MB), `@` file-mention dropdown + chips, edit-queued flow. Leaving edit mode without saving (the queued message was removed, or it drained into its own turn) drops the text that edit loaded into the field — the field is uncontrolled, so otherwise that text would stay and a later Enter would submit it as a brand-new message; anything the user typed after it stays. Memoized. |
| `parseCommandInput.ts` | `parseCommandInput(raw)` → `{ isCommand, prefix }` for the `/`-command menu. |
| `reasoning.ts` | `countWords(text)` — word count for the thinking note's header. A scan, not `split(/\s+/)`: it runs on every streamed frame over a growing buffer, so it must not allocate an array per call. Words rather than tokens because the renderer has no tokenizer. |
| `ToolCallCard.tsx` | Renders a tool call in a compact micro-bar layout (badge, summary, status hairline, expandable diff/output body). Memoized. When `collapseWhileRunning` is true (passed by `ToolCluster`), the card never auto-opens — even while the call is `pending` — so a long run of tool steps stays collapsed and the feed reads as a tight group. A `pending → done` re-key closes the card even if the user had clicked it open during the run. Edit-style calls (`edit`, `write`, `apply-patch`) show their `+N −M` line counts (from `diffStats`) in the header. Inside a cluster a step renders as a plain list row (no coloured left rule, no caret, lowercase badge; the ✓/✗ carries status), and a bash row drops the leading `cd <dir> &&` (`stripCdPrefix`; the hover title keeps the full command). |
| `ToolCluster.tsx` | Wraps **every** `tool` item (even a lone call) — plus the reasoning-only assistant messages between those calls, as `thought` steps (`ClusterStep`; dim `thought` badge, italic first-line preview, full text on open) — in one Claude-style line; with `live` (newest row of a running turn) and no pending step the line reads `Thinking…` with the spinner. Thoughts that never meet a tool stay ordinary bubbles. The line is **collapsed by default** and without card chrome: `summarizeCalls` text (`Read 2 files, edited a.ts, ran a command`), `+N −M` from `diffStats`, a red `· N failed`, trailing caret. While a step is pending the line names it with a spinner + `done/total` (`describeRunning`). Opened, the inner `.tool-call` cards sit in one framed list with a 1px hairline between them. Always passes `collapseWhileRunning` to every inner `ToolCallCard` so steps stay collapsed even while running (the cluster line already names the active step). Clustering happens at render time in `ChatPanel.tsx` via `clusterToolRows`, not in state. The helper also drops empty assistant messages (no text / reasoning / images) entirely from the rendered feed — the agent's loop persists these between tool batches (`if (textBuffer || calls.length > 0 || reasoningBuffer)` in `src/main/agent/loop.ts`) so without that drop, otherwise-consecutive tool calls would be scattered across 1-tool clusters on reload. `FeedMessage` already drops them at render, so the visible result matches a fresh live session. |
| `toolSummary.ts` | Pure helpers for the cluster line: `summarizeCalls`, `describeRunning`, `diffStats`, `stripCdPrefix` (unit-tested in `tests/unit/chat-tool-summary.test.ts`). |
| `MarkdownText.tsx` | Markdown rendering via `marked` + `marked-katex-extension` (LaTeX/KaTeX math rendering) + `DOMPurify.sanitize` (MathML whitelist). |
| `DiffView.tsx` | Inline diff view for edit tool calls. |
| `ContextFooter.tsx` | Context readout — a 2rem ring button (`--radius-xs`, `--bg-hover` on hover/open) that opens the **context panel** through `BaseDropdown` (`placement="top-end"`, portaled). The panel shows `context` / `tokens` / `cost`, then a breakdown of the next request: a stacked `.context-bar` plus one row per bucket (`System prompt`, `Instructions`, `Memory`, `Memory index`, `Skills`, `Mode`, `Tools`, `MCP tools`, `Messages`, `Free space`) with tokens and share of the window; `Tools` / `MCP tools` / instruction-file / skill rows expand to per-item counts (largest first). Row numbers are `estimateTokens` estimates while the header count is provider-reported, so the bar is scaled to fill exactly the used span. Fetches a fresh breakdown on open via the `onOpen` callback. |
| `TodoCard.tsx` | The session todo list as a transcript row: `ChatPanel` renders it after the feed rows and right above the pending prompt, so it scrolls with the feed (not sticky). Neutral hairline card: `Tasks` header + `done/total`, one row per todo with a Lucide mark (`Check` / spinning `Loader2` / `Circle` / `X`); the in-progress task spins and its text pulses (both off under `prefers-reduced-motion`). The header toggles a collapsed state that keeps naming the active task. Hidden when the list is empty. Memoized. |

## Conventions

- Feed updates are batched per animation frame (`flushDeltas`) to avoid input lag — keep streaming hot paths cheap.
- `FeedMessage`/`ToolCallCard` are memoized; update copy-on-write (never mutate items in place) so memo works.
- Message queue: prompts sent while a turn runs are queued in main. The renderer shows them in the composer's `.chat-queue` card (not the transcript) with send-now / edit / remove — `window.api.sendQueuedNow` promotes the message to the head and aborts the running turn, so it starts immediately instead of steering into it at the next loop step; `removeQueued` / `editQueued` are unchanged. A queued message can leave the queue without being sent (removed, or drained into its own turn) — `queue-updated` then clears `editTarget` if it pointed at that message, so the composer returns to Send/Stop instead of staying in `Save edit` and routing the next Enter to `editQueued` for a message that no longer exists (which cleared the field and sent nothing).
- Images travel as dataURL strings in `ImageAttachment`; only image/* accepted.
